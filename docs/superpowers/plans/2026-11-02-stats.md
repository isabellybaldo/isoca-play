# Stats Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Record one line per finished game on the server, and show the totals on a stats screen in the app and, without dates or times, on the public login page.

**Architecture:** A pure `track()` function watches each game's save change and keeps a `run` of counters inside the save; finished games go to a device outbox and on to `POST /api/stats/game`. `stats.py` stores them and works out the totals on request. The login page gets its section as server-rendered HTML, so nothing new becomes public except that HTML.

**Tech Stack:** FastAPI, SQLite, React, TypeScript, vitest, pytest.

**Spec:** `docs/superpowers/specs/2026-11-02-stats-design.md`

## Global Constraints

- No date, clock time or game-by-game list can be read without signing in.
- Anyone without a session cannot add, change or delete a record. `PUBLIC_PATHS` in `auth.py` does not grow.
- No timer or count appears on a game screen, and no game rule changes.
- A problem with stats never stops a game being played or saved, and never takes the login form with it.
- No save is ever sent for time alone; the save marker stays out of stats.
- A number built from nothing shows as a dash, never as zero.
- Migrations are appended, never edited.

## Review Focus

- A device whose storage is denied (tests already mock `getItem` and `setItem` to throw): the game plays on, and nothing is recorded. Test in Task 5.
- A save from before this shipped, or with a malformed `run`: it plays on and is never recorded. Test in Task 4.
- Reloading a won game, or replacing it later: one record, not two. Test in Task 4.
- A device clock set wrong or a sent-twice record: an odd day is stored as given, and the same id stores once. Test in Task 1.
- A database error on the login page: the form is served without the stats. Test in Task 3.

### Task 4: Counting a game as it is played

**Files:**
- Create: `web/src/stats/run.ts`
- Modify: `web/src/useSavedGame.ts` (`run?: Run` on all three types in `Saved`, the top level of a mahjong save, alongside `layout`)
- Test: `web/src/stats/run.test.ts`

**Interfaces:**
- Produces:

```ts
export type Run = { id: string; seconds: number; returns: number; tips: number; days: string[]; unsolved: number; turns: number; done: boolean };
export type GameRecord = { /* the Task 1 body */ };
export type Tick = { today: string; seconds: number; tips: number; newId: () => string };
export function track<G extends GameName>(game: G, prev: Saved[G] | null, next: Saved[G] | null, tick: Tick):
  { save: Saved[G] | null; records: GameRecord[]; spent: boolean };
```

`spent` says `tick.seconds` and `tick.tips` went into the run, so the caller can reset them.

Rules `track` follows, one game at a time, with "deal" being mahjong `state.tiles`, solitaire `deal` and sudoku `puzzle`:
- A new deal, or `next` null: `prev` with a valid run that isn't `done` and has days gives a record: `lost` if its status is `lost`, else `abandoned`. The new deal gets a fresh run.
- Same deal and no valid run: nothing changes. This is a save from before this shipped.
- `history` longer: add today to `days` once, spend the tick, and count a `turns` for a solitaire `'r'`.
- `history` shorter: `returns + 1`, spend the tick.
- Status newly `unsolved`: `unsolved + 1`.
- Status newly `won` and not `done`: a `won` record, and `done: true`. Nothing after `done` makes another.
- Anything else (a selection, a mode switch): the same object back, so `MOVED` still sees no move.

### Task 6: Wire it into the games

**Files:**
- Create: `web/src/stats/useTracked.ts`
- Modify: `web/src/App.tsx`, `web/src/mahjong/MahjongGame.tsx`, `web/src/solitaire/SolitaireGame.tsx`, `web/src/solitaire/SolitaireTable.tsx` (`useTip`'s `ask`), `web/src/sudoku/SudokuGame.tsx`
- Test: `web/src/stats/useTracked.test.tsx`, `web/src/App.test.tsx`, and a check on `web/public/sw.js` in `web/src/offline.test.ts`

**Interfaces:**
- Consumes: `track`, `addRecords`, `sendRecords`, the `useSavedGame` result.
- Produces: `useTracked(game, saved) -> { onGame, giveUp, tracker }`, where `tracker: Tracker = { tip(): void; onScreen(on: boolean): void }`. Each game takes an optional `tracker?: Tracker`, so its existing tests stand. `onGame` wraps `saved.setState`, and `giveUp` runs `track(state, null)` first.

Pending seconds and tips live in a ref, reset when `spent` is true. The clock runs only between `onScreen(true)` and `onScreen(false)` while `document.visibilityState === 'visible'`, measured with `performance.now()`. Each game screen calls `onScreen` from an effect on mount and unmount. `today` is the device's local date. `App` also calls `sendRecords()` on load and on the `online` event, and `logOut` waits for it for at most 1 second before going on. `track` may run twice for one update; the outbox's id check makes that harmless.
